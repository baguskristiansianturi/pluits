# CSS Ownership and Cascade Contract 001

**Status:** IMPLEMENTATION GOVERNANCE BASELINE — visual values remain subject to the existing approval lifecycle.  
**Applies to:** Every PLUITS route, feature, reusable component, and responsive state.  
**Runtime foundation:** `src/design-system/tokens.css`, `src/styles/global.css`, `src/design-system/page-shell.css`, and feature/component stylesheets.

## 1. Purpose

This contract defines exactly which layer owns structure, visual presentation, reusable values, and interaction. Its purpose is to prevent competing declarations, accidental overrides, and edits that appear to have no effect because another rule wins in the CSS cascade.

**The existing visual design is the baseline. This contract does not authorize a redesign, arbitrary resizing, spacing changes, or a bulk CSS rewrite.**

## 2. The responsibility split

| Concern | Authoritative owner | What belongs there | What does not belong there |
|---|---|---|---|
| Document/UI structure | HTML markup generated by the feature | Semantic elements, parent/child relationships, order, IDs, classes, data attributes, ARIA labels/roles | Visual spacing, colors, dimensions, typography, responsive layout |
| Visual presentation | CSS | Width/height, min/max dimensions, typography, color, borders, backgrounds, shadows, alignment, layout, spacing, positioning, visibility and responsive rules | Business decisions, navigation destinations, API calls |
| Shared reusable values | Design tokens, implemented as CSS custom properties | Approved/provisional platform-wide colors, spacing values, radii, breakpoints, containers, shared dimensions and layers | A page's one-off placement or interaction |
| Shared component appearance | Component/design-system CSS | Component anatomy, default geometry, variants and visual states | Feature-specific business logic |
| Feature/page composition | Feature/page CSS | Local grid/flex composition, page-specific alignment and placement, scoped responsive adjustments | Redefining global shell, brand, typography or shared component contracts |
| Interaction and application state | JavaScript/feature controller | Click behavior, navigation, state, API operations, permission checks, adding/removing state classes | Becoming a second styling system through arbitrary inline style mutations |
| Asset identity | Canonical asset/icon registry | Which logo/icon artwork is used and its stable semantic identity | Consumer-specific size, position, spacing, color or click behavior |

**HTML defines what exists and how elements relate. CSS defines how those elements look and where they are placed. JavaScript defines what happens.** A class or data attribute in HTML is a hook for CSS/JavaScript; it is not itself a second owner of dimensions.

## 3. Who owns each measurement?

| Measurement / property | Owner | Correct CSS mechanism |
|---|---|---|
| Element width and height | CSS rule of the component/feature that owns the element | `width`, `height`, `min-width`, `max-width`, etc. |
| Icon artwork identity | Icon registry | Semantic icon name / canonical SVG |
| Icon rendered size | Consuming icon component or feature | Size on the icon wrapper, e.g. `.ui-icon` |
| Button/touch target size | Button or interactive component | Width/height/min-height/min-width on the control, independently of the icon |
| Space between siblings | Parent layout | `gap`, `row-gap`, `column-gap` on the flex/grid parent |
| Space inside an element | That component | `padding` / logical padding properties |
| Space outside an element | That component's layout relationship | `margin` / logical margin properties |
| Distance from right/left/top/bottom edge | The positioned element, relative to its documented containing block | `inset-inline-end`, `inset-inline-start`, `top`, `bottom` (or equivalent inset properties) |
| Responsive changes | Same CSS owner as the property being adapted | A scoped media/container query that changes that owner's rule |
| Shared navbar/footer/page-shell geometry | Design-system page shell | Tokens in `tokens.css`, enforced in `page-shell.css` |
| Page-specific layout inside the shell | Owning feature/page stylesheet | Scoped feature/page selectors |

Important distinctions:
- `gap` belongs to the parent that arranges siblings. It does not create space between arbitrary unrelated elements.
- `padding` is inside an element's border.
- `margin` is outside an element.
- `right`/logical end inset positions an element from its containing block's edge; it is not the same as padding.
- An icon's SVG dimensions and its button's clickable/touch area are separate measurements.
- A token is a named reusable value, not a competing styling language. It is a CSS custom property consumed by CSS.

## 4. Rule ownership and precedence

Use the narrowest owner that correctly represents the design decision:

1. **Platform-wide repeated decision:** define/reference a token in `src/design-system/tokens.css`.
2. **Shared reusable component decision:** define it in that component's canonical stylesheet and consume platform tokens where appropriate.
3. **Feature composition decision:** define it in the owning feature stylesheet.
4. **One page-only exception:** scope it to that page and document why it is genuinely unique.
5. **Interaction state:** JavaScript may toggle a semantic class or attribute; CSS owns the resulting visual state.

A lower-level page rule must not silently redefine an upstream shared contract. A global token must not be changed to solve a single page's local alignment issue.

Within the same owner, keep one authoritative declaration for a property in each applicable state/viewport range. Responsive declarations are allowed when they intentionally adapt that property. A later override is not a substitute for editing the original owner rule.

When a property appears more than once:
- determine whether it is a deliberate state/viewport variation or an accidental duplicate;
- inspect selector specificity, source order, media-query conditions, inheritance, inline styles and JavaScript mutations;
- preserve the current computed result before consolidation;
- consolidate only after all affected states and viewports are verified.

Do not append another override at the bottom of a stylesheet to make a change "win". Do not use `!important` to bypass ownership or cascade analysis. Any exceptional use requires a documented reason and bounded scope.

## 5. Tokens versus local CSS values

A token is appropriate when a value represents a reusable platform decision (for example, page gutters, standard spacing steps, common radii, brand colors or shared shell dimensions).

A local CSS value may remain local when it describes a unique composition or a component-specific measurement that is not a platform-wide standard. Do not create a global token for every number merely to eliminate numbers from CSS. Do not replace an existing local value with a nearby token if doing so changes the visual result.

Token values marked provisional remain provisional. This contract does not approve or normalize any existing numeric value.

## 6. Runtime ownership map

| Runtime path | Ownership |
|---|---|
| `src/design-system/tokens.css` | Shared CSS custom properties and platform-wide design values |
| `src/styles/global.css` | Browser baseline, global typography/color inheritance, generic primitives such as the base `.ui-icon` wrapper |
| `src/design-system/page-shell.css` | Shared header, footer, shell geometry and shared navigation contracts |
| `src/design-system/page-shell.js` | Shared shell markup/rendering; no page-specific visual measurements |
| `src/design-system/icons.js` | Canonical icon identity and artwork; no consumer layout or action |
| `src/features/<feature>/*.js` | Feature markup and interaction wiring |
| `src/features/<feature>/*.css` | Feature-owned presentation and responsive composition |
| `PLUITS-MASTER-MODEL-APP/06-PLATFORM-UI-FOUNDATION/` | Governing specifications, registries, approval status and change procedures |

A feature may provide content/actions to a shared component slot. It may not take ownership of the shared component's geometry by redefining its base selectors.

## 8. Safe change procedure

For every future measurement or spacing change:

1. Identify the exact element/component and the visible edge or relationship being adjusted.
2. Identify the owning layer from the runtime ownership map.
3. Find every declaration of the target selector/property, including media queries and state selectors.
4. Determine the current winning declaration for each supported viewport/state.
5. Record the current value and its containing block/relationship (for example, right inset from profile-card edge).
6. Change the existing owner declaration; do not add a competing override.
7. Check that unrelated properties (icon artwork, hit area, position, action, neighboring layout) remain unchanged.
8. Run architecture, unit, build and relevant feature tests.
9. Verify rendered computed styles and screenshots at relevant viewport widths and interaction states. Source-string tests alone are not visual verification.
10. Update the owning specification/audit and consumer map. Report any viewport not actually verified.

## 9. Profile stylesheet remediation sequence

The profile CSS must be cleaned in controlled slices, not rewritten wholesale:

1. Inventory each profile component and map all declarations by selector, property, media query and state.
2. Establish a rendered baseline for the supported mobile/tablet/desktop widths and key interactions.
3. Consolidate one component at a time, retaining the same computed styles at each tested width.
4. Keep unique visual treatments and responsive differences; remove only proven dead or redundant declarations.
5. Run the profile feature tests and full application test/build suite after each slice.
6. Compare before/after screenshots and computed styles before accepting the change.

**No runtime CSS, HTML, JavaScript, token value, icon artwork, page geometry or interaction was changed by this audit document.** Runtime cleanup is intentionally gated on a browser baseline so the existing design is not changed by guesswork.

## 10. Completion criteria

A CSS ownership cleanup is complete only when:
- each shared or local visual property has a documented owner;
- no accidental competing declarations remain in the cleaned scope;
- all intentional responsive/state variations are preserved;
- existing computed values and visual output are unchanged unless separately approved;
- relevant tests pass;
- viewport evidence is recorded honestly;
- the implementation map and canonical documentation agree.
